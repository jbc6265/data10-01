이 문서는 제출자가 패들릿에 올린 게시물과 그 아래 본인 댓글(`docs/source/패들릿_접수_원문.md`)을 과정 기획서 형식(10장)으로 정리한 것입니다.
첨부 파일은 없어, 열 구성·수명 기준·오버홀 주기는 모두 **가정**이며 10장에서 확인합니다.

## 1. 추진 배경과 현안

- 굴착기 카운터웨이트를 찍는 프레스는 설비 트러블이 나면 생산이 멈추고, 금형이 수명을 넘겨 쓰이면 품질·파손 위험이 커집니다.
- 지금은 프레스 진동·전류·온도·타수 데이터가 있지만, 이를 모아 **이상 징후를 미리 알리거나 금형 교체·오버홀 시기를 챙기는 체계**는 없는 것으로 보입니다(가정).
- 제출자는 협력사 MES 구축을 지원하는 직무라, 도구는 **협력사가 외부 망에서 웹 페이지로 접속해 쓸 수 있어야** 합니다(댓글 ⑥).

## 2. 목표

### 2.1 최종 목표 (제출 기대 산출물 ④ · 댓글 ⑧)

| 번호 | 결과물 |
|---|---|
| ① | 프레스 이상 감지 알림 |
| ② | 금형별 타수 집계 |
| ③ | 금형 교체주기 알림 |
| ④ | 프레스 정기 오버홀 알림 |
| ⑤ | 월별 프레스 종류별 타수 집계 보고서 |

성공하면: 프레스·금형 예지보전으로 설비 트러블을 막고, 금형 수명을 관리합니다.

### 2.2 1차 개발 목표

규칙으로 바로 계산할 수 있는 것(타수 집계·교체 주기·오버홀)을 먼저 완성하고, 이상 감지는 **통계 기준(평소 값 대비 벗어남)** 으로 「주의·점검 필요」를 표시하는 데까지 만듭니다.
고장 기록으로 배우는 예지(학습형 예측)는 고장·교체 이력이 모여야 하므로 2단계로 둡니다.

## 3. 보유 데이터

| 데이터 | 형태 | 규모·주기 | 비고(민감도 등) |
|---|---|---|---|
| 프레스 센서 로그 — 일자(초까지)·프레스·프레스 종류·금형명·프레스 누적 타수·금형 타수·전류(A)·전압(V)·온도(℃)·진동(mm/s) | CSV(UTF-8, 모든 칸 따옴표) — **2차에 받은 모의 로그 형식** | 센서 값 2초마다, 타수는 10초에 1타 → 프레스 1대 하루 43,200행 | 설비 운전 값이라 개인정보 없음. 받은 것은 수강생이 만든 모의 데이터(2시간·1대) |
| 프레스 진동 | 위 로그의 「진동(mm/s)」 칸 | 2초 | 2차에 확인 — RMS 인지 피크인지는 확인 필요 |
| 금형 타수 | 위 로그의 「금형 타수」 칸 | — | **교체 때 0 으로 돌아가는 누적 카운터**로 확인(받은 로그 0 → 719). 1단계의 「그 행에서 친 횟수」 가정을 바꿈 |
| 일일 로그(가동 시간 포함) | 미상 | 하루 한 행 | 1단계 형식. 계속 쓸 수 있게 두었고, 2초 로그는 하루 묶음으로 바꿔 같은 판정에 이어 붙임 |
| 고장·금형 교체·오버홀 이력 | 없음(제출 자료에 언급 없음) | — | 예지 정확도를 높이려면 꼭 필요 — 10장 |
| 금형 수명 기준 타수·오버홀 주기 | 없음 | — | 1단계는 설정 화면에서 사용자가 입력 |

1단계는 첨부 파일이 없어 칸 이름 그대로 만든 **가상 샘플**(프레스 P1~P4 × 90일, 금형 M-01~M-08)로 개발했습니다.
2차에서 받은 로그 형식(2초 센서 로그)은 그대로 가져와지도록 맞췄고, 같은 형식의 가상 샘플(4대 × 3일)을 새로 만들었습니다(11장).

## 4. 해결 방안 개요

```mermaid

  X[프레스 로그<br/>엑셀·CSV 여러 개] --> M[열 연결·정리<br/>날짜·프레스·금형·타수·센서]
  MS[설비·금형 기준표<br/>수명 타수·오버홀 주기] --> R
  M --> T[행마다 타수<br/>타수 열 또는 누적 차이]
  T --> R[규칙 계산]
  R --> D1[금형 타수 집계<br/>교체 예정일]
  R --> D2[오버홀 알림]
  M --> S[이상 감지<br/>기준선 대비 ±kσ·지속 조건]
  D1 --> DB[대시보드<br/>정상·주의·점검 필요]
  D2 --> DB
  S --> DB
  T --> RP[월별 프레스 종류별<br/>타수 보고서]
  DB --> AI[AI 프롬프트<br/>계산된 사실만·이름 가림]
```

| 단계 | 내용 |
|---|---|
| 수집 | 프레스 로그(엑셀·CSV), 설비·금형 기준표 |
| 정리 | 열 연결, 날짜·숫자 읽기, 같은 행 중복 제거, 타수 계산(타수 열 → 프레스 누적 차이 → 금형 누적 차이) |
| 분석 | 금형 사용 타수·사용률·교체 예정일, 오버홀 주기 사용률·예정일, 채널별 기준선 대비 이상, 월별 종류별 집계 |
| AI | 계산된 사실만 담은 프롬프트로 요약·확인 항목·정비 일정 제안(반자동, 이름은 별칭으로) |
| 산출물 | 대시보드, 금형·오버홀 화면, 이상 감지 그래프, 월별 보고서(엑셀·인쇄) |

7. 협력사 공유·학습형 예지 — 2단계 이후

## 7. 기술 구성

| 과정 도구 | 이 프로젝트에서 쓰는 곳 |
|---|---|
| DAY1 암묵지 자산화·전략기획 | 보전 담당자가 「이상하다」고 보는 기준, 금형 교체·오버홀 판단 기준을 꺼내 기준표로 적기 |
| DAY2 코랩(Python)·바이브코딩 | 로그 정리, 타수 계산, 기준선·관리한계 시험, 웹 도구 제작 — 1단계의 중심 |
| DAY3 멀티모달 비정형 정보화 | 수기 점검표·정비 일지 사진에서 고장·교체 이력 뽑기 (2단계) |
| DAY4 RAG (Dify, NotebookLM) | 설비 매뉴얼·정비 기준서를 근거로 이상 원인·점검 항목 질의 (2단계) |
| DAY5 Make 자동화 | 점검 필요 알림 보내기, 월별 보고서 정기 발송 (2단계) |
| 생성형 AI | 상태 요약·확인 항목·정비 일정 제안 (1단계는 반자동) |

**개발 형태**

- 1단계는 **설치 없이 브라우저에서 도는 정적 웹 페이지**입니다(HTML·JavaScript, 빌드·서버 없음). 내 PC 에서 파일로 열어도 되고, GitHub Pages 주소로 열어도 됩니다.
- **외부 망·협력사 접속(댓글 ⑥)**: GitHub Pages 주소는 회사 밖 어디서나 열립니다. 다만 1단계는 데이터를 **각자의 브라우저 안에만** 저장하므로, 협력사가 같은 주소로 들어와도 서로의 데이터는 보이지 않습니다(각자 자기 로그를 넣어 씀). 백업 JSON·기준표 엑셀로 주고받을 수는 있습니다.
- 협력사가 **같은 데이터를 함께 보려면** 로그인과 공유 DB 가 필요합니다. 2단계에서 Supabase(협력사별 계정·권한)로 만듭니다. 그때 어떤 협력사가 무엇을 볼 수 있는지(권한)를 먼저 정해야 합니다(10장).
- AI 는 도구가 직접 부르지 않는 **반자동**이 기본입니다. 계산된 숫자만 담고 프레스·금형 이름은 「설비1」「금형1」로 가립니다. 본인 키로 OpenAI 호환 서버에 바로 보내는 것도 고를 수 있습니다(키는 리포에 없음).

## 8. 개발 단계

### 1단계 — 지금 개발 가능한 부분

로그 칸 이름(댓글 ⑦)만으로 만들 수 있는 것을 먼저 만들었습니다. 고장 이력이 없으므로 이상 감지는 **통계 기준의 「주의」 표시**까지입니다.

- 로그 가져오기(엑셀·CSV 여러 개, 열 연결, 같은 행 중복 제거, 행 점검 알림)
- 타수 계산 — 타수 열이 있으면 그 값, 없으면 프레스 누적 타수 차이, 그것도 없으면 금형 누적 타수 차이. 둘 다 있으면 서로 맞는지 점검
- 설비·금형 기준표(화면 입력·엑셀 주고받기), 금형 교체·오버홀 완료 기록 버튼
- 금형별 타수 집계·교체 예정일(최근 14일 일평균), 오버홀 알림(타수·일수)
- 이상 감지 — 채널별 기준선(중앙값·MAD 또는 평균·표준편차), ±kσ 관리한계, 지속 조건(연속 일수), 근거 숫자, 관리도 그래프. 기준값은 설정에서 바꿈
- 대시보드 — 프레스별 정상·주의·점검 필요, 금형 수명 사용률, 다가오는 정비 일정
- 월별 프레스 종류별 타수 보고서(엑셀·인쇄)
- AI 프롬프트(사실만, 이름 가림, 답의 별칭 되돌리기)
- 가상 샘플(프레스 4대 × 90일)에 세 가지를 심어 확인: 금형 M-05 수명 임박(주의), P2 마지막 2주 전류·온도 상승(점검 필요), P4 오버홀 주기 지남(점검 필요)

### 2단계

- 실제 로그로 열 연결·단위·타수 계산 방식 확정, 기준선 구간·k·지속 일수를 실제 잡음에 맞춤
- 고장·금형 교체·오버홀 이력을 받아 이상 감지 결과와 맞춰 보기(얼마나 미리 알렸는지, 헛경보가 얼마나 되는지)
- 협력사 공유 — Supabase 로그인·협력사별 권한·공유 DB
- 점검 필요 알림 보내기(Make 등)

### 3단계

- 학습형 예지 — 고장 전 패턴 학습, 금형 남은 수명 예측
- PLC·설비 화면에서 로그 자동 수집

## 9. 기대 효과

- **설비 트러블 예방** — 전류·온도처럼 서서히 오르는 변화를 고장 전에 「점검 필요」로 드러냅니다.
- **금형 수명 관리** — 금형마다 사용률과 교체 예정일을 보며 교체를 미리 준비합니다.
- **오버홀 누락 방지** — 주기를 넘긴 프레스를 빠짐없이 표시합니다.
- **보고 시간 단축** — 월별 프레스 종류별 타수 보고서를 같은 형식으로 바로 냅니다.

제출 자료에는 정량 수치가 없어 이 문서도 수치를 적지 않습니다.

## 10. 확인 필요 사항

**2차에서 풀린 것** — 로그 견본(1번, 2초 로그 형식), 「금형 타수」의 뜻(4번, 교체 때 0 으로 돌아가는 누적), 진동 수집 여부(5번, 로그에 있음)

**샘플 데이터 (남은 것)**

1. **관리 한계를 잡을 「정상 기준 구간」** — 설비가 정상이던 날·시간대(예: 오버홀 직후 하루, 예열이 끝난 뒤). 지금은 처음 1시간(1,800개)을 기본으로 씁니다
2. 고장·금형 교체·오버홀 이력 — 언제, 어느 프레스·금형, 무엇이 고장났는지(있는 만큼). ±3σ 이탈이 실제 고장 전에 나타났는지 맞춰 보는 데 꼭 필요합니다
3. 금형별 수명 기준 타수, 프레스 종류별 오버홀 주기(타수 또는 개월)
4. 실제 설비 로그 하루치 이상(가능하면 며칠) — 받은 것은 모의 2시간이라 하루 안의 변화(예열·점심 정지·교대)와 날마다의 차이를 아직 못 봤습니다
5. 진동 값이 RMS 인지 피크인지 · 정지 중에도 센서 값이 계속 들어오는지(정지 구간을 관리도에서 뺄지 정함) · 「10초에 1타」가 금형·제품마다 같은지

**데이터 출처·환경**

6. 데이터를 어디서 꺼내는지 — PLC, 설비 화면 내보내기, 수기 엑셀 가운데 무엇이고, 얼마나 자주 꺼낼 수 있는지(「실시간」을 몇 분 간격 파일로 볼지, 설비에서 바로 받아야 하는지)
7. 협력사 계정·공유 방식 — 협력사마다 자기 프레스만 보는지, 협력사육성팀이 전체를 보는지, 몇 곳·몇 명인지
8. 외부 AI(ChatGPT 등)에 설비 로그 요약을 보내도 되는지, 회사에서 허용한 AI 가 있는지

## 11. 2차 반영 내역 (2026-10-21)

수강생이 보낸 로그 샘플(2초 간격 모의 데이터 3,600행)과 요청 — 「전류·전압·온도·진동은 센서가 2초 단위로 보내고, 타수는 10초에 1타씩 오르는 로그다. 대시보드에 시각화하고 값마다 ±3σ 관리선으로 관리하고 싶다」 — 을 반영했습니다.

### 11.1 받은 로그로 확인한 것

| 항목 | 확인 결과 |
|---|---|
| 형식 | CSV · UTF-8(BOM) · 모든 칸 따옴표 · 11열(「데이터 구분」 칸은 읽지 않음) |
| 간격 | 일자 칸에 초까지(yyyy-mm-dd hh:mm:ss), 2초 간격 — 1대 하루 43,200행 |
| 타수 | 프레스 누적 타수가 10초에 1씩 오름(2시간 719타, 기준 720타의 99.9%) |
| 금형 타수 | 0 에서 시작해 719 까지 오르는 **누적 카운터** — 1단계 가정(그 행에서 친 횟수)을 바꿈 |
| 센서 값 | 앞뒤 값이 거의 같음(자기상관 — 전류 0.96, 온도 0.99). 온도는 2시간 동안 약 1.2℃ 오름(예열로 보임) |

### 11.2 반영한 기능

| 요청 | 반영 |
|---|---|
| 이 CSV 를 그대로 가져오기 | 앞부분(512KB)으로 2초 로그인지 가리고, 맞으면 파일을 4MB 조각으로 나눠 끝까지 읽음(따옴표·BOM·조각 경계 처리, CP949 도 판별). 21MB(17만 행) 파일을 1.5초 안에 읽고 화면 멈춤은 0.4초 이하(헤드리스 실측). 같은 프레스·같은 시각은 한 번만 셈. 프레스마다 IndexedDB 에 저장 |
| 대시보드에 시각화 | 새 화면 「실시간 관리도」 — 프레스·금형·보는 구간(전체·최근 10분~하루·기간 지정) 고르기, 채널마다 마지막 값 카드, 전류·전압·온도·진동 관리도 4장. 대시보드 맨 위에 프레스별 「2초 센서 — 마지막 값」(최근 1시간 이탈·가동 중/정지) |
| 값마다 ±3σ 관리선 | Shewhart 관리도 — 중심선(기준 구간 평균), ±3σ 관리선(UCL·LCL), ±2σ 경고선(선택), 관리선 밖 점은 빨간 점. 점이 많으면 시간 칸마다 평균·최소·최대로 줄여 그리되 이탈점은 줄이지 않음 |
| 관리 한계 기준 | 기준 구간 = 처음 N개(기본 1,800개 = 1시간) 또는 기간 지정. σ = 표본 표준편차(기본) 또는 이동범위 MR̄/1.128(I-MR) — 화면에 기본값과 이유를 적음 |
| 이상 판정 규칙 | 1점 ±3σ 밖(늘) + 선택: 연속 9점 한쪽 · 연속 6점 증가·감소 · 3점 중 2점 ±2σ 밖. 이어진 이탈점은 한 번으로 묶어 목록(최근 것부터)·엑셀(이탈 목록·관리 한계·정지·금형 리셋·시간별 타수) |
| 10초에 1타 | 누적 타수 차이로 타수·시간당 타수·기준(10초 1타) 대비·시간 가동률, 60초 넘게 타수가 안 오르면 정지 구간, 30초 넘게 기록이 없으면 기록 끊김, 금형명이 바뀌거나 금형 타수가 줄면 「금형 리셋(교체)」 |
| 기존 일 단위 판정 | 2초 로그를 프레스·날짜·금형마다 하루 한 행(타수 합·가동 시간·정지 아닌 값의 평균)으로 묶어 기존 금형 수명·오버홀·「최근 14일 vs 앞 42일, ±3σ 3일 연속」 판정과 월별 보고서에 이어 붙임 |

### 11.3 기본값과 그 이유

- **σ 는 표본 표준편차가 기본입니다.** 하나씩 재는 값의 표준 관리도(I-MR)는 이동범위(MR̄/1.128)로 σ 를 잡지만, 2초 값은 앞뒤가 거의 같아 이동범위가 아주 작게 나옵니다. 받은 로그로 재 보니 이동범위 방식은 처음 1시간 기준으로 온도 3,425점·전류 2,520점(3,600점 중)이 관리선 밖이었고, 표본 표준편차는 0점이었습니다.
- **「연속 9점 한쪽」 같은 추가 규칙은 기본은 끔.** 같은 이유로 2초 값에서는 정상이어도 아주 자주 걸립니다(받은 로그 전류 3,600점 중 3,086점). 「1분 평균」으로 묶어 볼 때 켜면 평균이 옮겨 간 것을 잡습니다(샘플 P4 전압).
- **정지 구간 값은 관리도에서 뺌(기본).** 정지하면 전류·진동이 떨어져 늘 이탈로 나오기 때문입니다. 정지 구간은 따로 표로 보입니다.
- **2초 원값은 정상이어도 370개에 1개꼴(약 12분에 한 번) ±3σ 를 넘습니다.** 그래서 이어진 이탈점을 한 번으로 묶고, 「1분 평균·5분 평균」으로 묶어 보는 보기를 두었습니다.
